Design Patterns — Glossary

Shared vocabulary for the blog series. Every lesson and post sticks to these definitions. Grows one pattern at a time.

Creational pattern category
A pattern about how objects get made — hiding or organizing instantiation. Series so far: Singleton, Builder. Queued: Factory Method, Abstract Factory, Prototype.
Product builder
The complex object under construction. It carries data and behavior but knows nothing about how it gets built.
Builder (interface) builder
Declares the construction steps, abstracted from any concrete implementation. In TS: an interface whose steps return this.
Concrete Builder builder
Implements the steps against a real product; holds the work-in-progress in a private field. build() hands the product over, then resets.
Director builder
Holds the recipes: which steps to call, in what order. Depends only on the builder interface. Optional — clients may drive the steps themselves (Refactoring.Guru).
Client builder
Code that picks a concrete builder and either hands it to a director (menu order) or chains steps directly (custom order).
Fluent API / method chaining technique
Methods that return the receiver so calls chain: b.setBread('rye').addDeck().build(). In TS, type the return as polymorphic this so subclasses chain correctly.
Telescoping constructor smell
A constructor (or overload pile) with many mostly-optional positional parameters: new Sandwich('rye', 2, 'swiss', [], true). The classic motivation for Builder.
Singleton pattern
Restricts a class to one instance and provides a global access point (private constructor + static getInstance()). Covered in the published post.
Builder pattern
Separates the construction of a complex object from its representation so the same process can create different representations (GoF). See the cheat sheet.

Canonical source: Design Patterns, Gamma, Helm, Johnson & Vlissides (1994). See also: builder cheat sheet · exercise 0001
